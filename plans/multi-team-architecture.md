# ENSEMBLE CAST — マルチチームアーキテクチャ構想

> ステータス: 構想段階（PoC未実施）
> 作成日: 2025-01-30
> 目的: 大規模プロジェクト対応のためのスケーリング設計

---

## 背景・課題

### 現状の限界

現在のENSEMBLE-CASTは「1チームが全体を見る」前提で設計されている。

```
Producer → Director → Cast (4-8名)
                ↓
        1つのプロジェクト全体を担当
```

**問題**: プロジェクトが成長すると...
- 横断的な依存関係が増加
- 1つの機能修正に3-5箇所以上の変更が必要
- **「どこを直すべきか探す」コストが爆発**
- コンテキスト限界に直撃（Claude の中規模対応限界の原因）

### 実例（2025-01-30 Phase 2テストで発生）

- Cast 1, 2 が作成したコンポーネントを
- Cast 3 が統合時に使用せず独自実装
- Reviewer は「動く」のでスルー
- Director も設計意図の逸脱を検知できず

→ これが大規模になると致命的な整合性問題に発展する

---

## 提案: マルチチーム・ドメイン分割アーキテクチャ

### コンセプト

```
┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│   Team A    │◄──►│   Team B    │◄──►│   Team C    │
│   (認証)     │    │   (課金)     │    │   (通知)     │
│             │    │             │    │             │
│  Leader     │    │  Leader     │    │  Leader     │
│  + Reviewer │    │  + Reviewer │    │  + Reviewer │
│  + Cast x2  │    │  + Cast x2  │    │  + Cast x2  │
└─────────────┘    └─────────────┘    └─────────────┘
       │                 │                  │
       └─────────────────┼──────────────────┘
                         ▼
              ┌─────────────────────┐
              │  Chief Architect    │
              │  (全体構造の薄い把握) │
              └─────────────────────┘
                         ▼
              ┌─────────────────────┐
              │ インターフェース契約  │
              │ (API定義・型・境界)   │
              └─────────────────────┘
```

### 核心的アイデア

1. **各チームは自分の担当機能だけ完全把握**
2. **関連機能はインターフェース（境界）のみ把握**
3. **チームリーダー同士が協議して開発を進める**

→ 人間の大規模プロジェクトと同じ構造

---

## なぜ実現可能か

### 1. 人間の組織と同じ構造

- 大規模開発は既にこの方式で動いている
- 誰も全体を完全把握していない
- インターフェース契約で協調できている

### 2. コンテキスト問題の回避

- 各チームは「自分の領域 + 境界のAPI」だけ把握すればよい
- フルコンテキストが不要になる
- Claude の限界を構造で回避

### 3. 責任の明確化

- 「認証の問題 → Team Aに聞け」
- 探す必要がなくなる
- 変更影響範囲が限定される

---

## 必要な仕組み

| 要素 | 内容 | 実装アイデア |
|------|------|-------------|
| **インターフェース定義書** | 各チームが公開するAPI/型/契約 | OpenAPI, TypeScript型定義, Proto |
| **変更通知プロトコル** | IF変更時の依存チーム通知 | `interfaces/` ディレクトリ + 変更検知 |
| **Chief Architect** | 全体構造を薄く広く把握 | 専用Agent（IF定義のみ読む） |
| **統合テスト** | チーム境界をまたぐ検証 | E2Eテスト + Contract Testing |
| **チーム間MTG** | 定期的なIF変更共有 | Leader間の同期プロトコル |

## 実装フェーズ（PoC計画）

### Phase 1: 2チーム構成での検証

```
Team Frontend          Team Backend
├── Leader             ├── Leader
├── Reviewer           ├── Reviewer
├── Cast (UI)          ├── Cast (API)
└── Cast (State)       └── Cast (DB)
```

共有:
- `interfaces/api-contract.yaml` (OpenAPI)
- `interfaces/types.ts` (共通型定義)

検証ポイント:
- チーム間通信は成立するか
- IF変更時に正しく通知されるか
- 統合時の問題は減るか

### Phase 2: リーダー間MTGの仕組み

- 定期的にIF変更を共有するプロトコル
- 影響範囲の相互確認フロー
- 非同期（ファイルベース）でのMTG

### Phase 3: スケールテスト

- 3-4チームに拡大
- 通信量が爆発しないか検証
- Chief Architect の負荷確認

### Phase 4: プロダクション適用

- 実際の中〜大規模プロジェクトで適用
- SKILLS/hooks との統合
- パフォーマンス・コスト評価

## 懸念点と対策

| 懸念 | 詳細 | 対策 |
|------|------|------|
| **N²通信問題** | チーム数増加で調整コスト爆発 | Chief Architect をハブにして星型構造に |
| **IF変更の検知漏れ** | 誰かが勝手にIF変えて壊れる | 契約書の自動検証（型チェック、CI） |
| **チーム間の認識齟齬** | 同じ用語を違う意味で使う | 用語集・ユビキタス言語の整備 |
| **統合の複雑さ** | 最後に全部繋げると動かない | 継続的統合（頻繁なマージ） |

## 将来ビジョン

### SKILLS との統合

- チーム共通のスキルをライブラリ化
- 「API呼び出しパターン」「エラーハンドリング」等を標準化
- 新チーム立ち上げ時に即座に適用可能

### hooks との統合

- IF変更時に自動で依存チームに通知
- 統合テスト自動実行
- Contract違反の自動検知

### 最終形態

```
Owner
  ↓
Producer (プロジェクト全体統括)
  ↓
Chief Architect (技術全体・IF管理)
  ↓
┌─────────┬─────────┬─────────┬─────────┐
│ Team A  │ Team B  │ Team C  │ Team D  │
│ Auth    │ Billing │ Notify  │ Admin   │
└─────────┴─────────┴─────────┴─────────┘
  各チーム: Leader + Reviewer + Cast x N
```

これが実現すれば、「中規模まで」の壁を突破し、
人間の大規模プロジェクトと同等の構造でAI開発が可能になる。
