# Swarm Development

設計書: $ARGUMENTS

---

## 即座に実行すること

**このプロンプトを読んだら、以下を順番に実行してください:**

1. 設計書 `$ARGUMENTS` を Read ツールで読み込む
2. 設計書の「実装タスク」セクションを確認
3. Phase 1 でタスク分析・構成決定
4. Phase 2 で開発を実行（バックグラウンド並列 + 2段階レビュー）
5. Phase 3 で統合・テスト
6. Phase 4 で Quality Gate 実行（証拠必須）

**待機や確認は不要です。すぐに行動を開始してください。**

---

## あなたの役割: Orchestrator（Architect）

**重要**: あなた自身がOrchestratorとして設計監視を担います。

### Architect 役割

1. **設計書の読み込みと理解**
   - 設計書を読み込む
   - 実装タスクと依存関係を把握

2. **既存コードとの整合性確認**
   - プロジェクトの既存コードベースを確認
   - 既存コードとの整合性をチェック

3. **Agent完了時の2段階レビュー**
   - 各Agentが完了したら、Spec Review → Quality Review を実行
   - 問題があれば修正ループを回す

---

## Phase 1: タスク分析・構成決定

### 手順

1. **設計書を読み込む**
   - `$ARGUMENTS` のパスから設計書を取得
   - 「実装タスク」セクションを特定

2. **タスクの依存関係を分析**
   - 独立して実行可能なタスクを特定
   - 依存関係のあるタスクをグループ化

3. **既存コードベースを確認**
   - 再利用可能なコードを特定
   - 重複実装を防止

4. **構成をユーザーに報告**

```
## Phase 1 完了 - タスク分析

### 設計書
`[設計書パス]`

### Developer Agent 構成
| Agent | 担当タスク | 依存 |
|-------|-----------|------|
| Dev1 | [タスク名] | - |
| Dev2 | [タスク名] | - |
| Dev3 | [タスク名] | Dev1 |
...

### 再利用コード
- [既存コードベースから特定したコード]

→ Phase 2 開始: Developer Agent を起動します
```

---

## Phase 2: Developer Agent 並列起動 + 2段階レビュー

### Step 2.1: Developer Agent をバックグラウンドで起動

**独立したタスクは1つのメッセージ内で複数のTask toolを同時に呼び出す。**
全て `run_in_background: true` で起動し、output_file パスを記録する。

Task toolパラメータ:
- `subagent_type`: `"general-purpose"`
- `description`: `"Dev[N]: [具体的なタスク名]"`
- `run_in_background`: `true` ← **重要: バックグラウンド実行**
- `prompt`: 以下のテンプレートを使用

```
## Role: Developer Agent [N] - [タスク名]

### タスク
[タスクの詳細説明]

### 設計書
`[設計書パス]` を参照。

### 実装内容
[設計書から該当セクションを抽出 - ファイルを読ませず直接記載]

### 開発ルール（必須）

1. **TDD（テスト駆動開発）**
   - まずテストを書く
   - テストが失敗することを確認
   - テストを通す最小限の実装
   - リファクタリング

2. **既存コード確認**
   - プロジェクトの既存コードベースで再利用可能なコードを確認
   - 重複コードを作成しない

3. **設計書に従う**
   - 設計書から逸脱しない
   - 不明点があれば設計書を再確認

---

## 実装開始前に（重要）

以下について不明点があれば、**実装前に質問してください**:
- 要件・受け入れ基準の解釈
- 実装アプローチ・戦略
- 依存関係・前提条件
- 設計書の曖昧な点

**推測せず、確認してから進めてください。**

---

## 自己レビュー（報告前に必須）

実装完了後、報告前に以下を自問してください:

**完全性:**
- 仕様の全要件を実装したか？
- 漏れた要件はないか？
- 未処理のエッジケースはないか？

**品質:**
- 名前は明確で正確か（動作を表す、実装方法ではなく）？
- コードは保守可能か？

**規律:**
- オーバービルドしていないか（YAGNI）？
- 要求されたものだけを作ったか？
- 既存のコードベースパターンに従ったか？

**テスト:**
- テストは実際の動作を検証しているか（モックの動作ではなく）？
- TDDに従ったか？

問題を見つけたら、報告前に修正してください。

以下の形式で報告すること：

## 完了報告

### 作成・修正ファイル

### テスト結果
- 実行コマンド: `[テストコマンド]`
- 結果: PASS/FAIL

- [懸念点があれば記載]

### 備考
[特記事項]

### スコープ外エラー（重要）
以下のエラーを検出した場合、無視せず必ず報告すること:
- 型エラー: [ファイル:行番号] [エラー内容]
- テスト失敗: [テスト名] [エラー内容]
- ビルドエラー: [エラー内容]
- リンターエラー: [ファイル:行番号] [エラー内容]

**「スコープ外なので無視」は禁止。報告すれば Fix Agent が対処する。**
```

### Step 2.2: 起動直後の報告

全 Developer を起動したら、簡潔に報告:

```
## Phase 2 開始 - 並列開発

| Agent | タスク | 状態 |
|-------|--------|------|
| Dev1 | [タスク名] | 🔄 実行中 |
| Dev2 | [タスク名] | 🔄 実行中 |
| Dev3 | [タスク名] | 🔄 実行中 |

完了次第、2段階レビューを実行します。
```

### Step 2.3: Agent完了時の2段階レビュー

**各Agentが完了したら、TaskOutput で結果を取得し、2段階レビューを実行する。**

#### Stage 1: Spec Review（仕様準拠確認）

**目的**: 実装が仕様通りか確認（過不足なく）

```
Task(
    subagent_type: "general-purpose",
    description: "Spec Review: Dev[N] - [タスク名]",
    prompt: """
    ## 仕様準拠レビュー

    ### 要求された仕様
    [設計書から該当タスクの仕様を抽出]

    ### 実装者の報告
    [Developer Agentの完了報告]

    ### 重要: 報告を信用しない

    実装者の報告は楽観的または不完全な可能性がある。
    **必ず実際のコードを読んで検証すること。**

    ### 確認項目

    **不足:**
    - 要求された全てが実装されているか？
    - スキップまたは漏れた要件はないか？

    **過剰:**
    - 要求されていないものを作っていないか？
    - 不要な機能追加やオーバーエンジニアリングはないか？

    **誤解:**
    - 要件の解釈が正しいか？
    - 間違った問題を解いていないか？

    ### 報告形式
    - ✅ 仕様準拠（コード確認済み）
    - ❌ 問題あり: [具体的に何が不足/過剰か、ファイル:行番号を含む]
    """
)
```

**Spec Review で問題が見つかった場合:**
1. Developer Agent を再起動して修正
2. 修正後、再度 Spec Review
3. ✅ になるまでループ

#### Stage 2: Quality Review（品質確認）

**Spec Review が ✅ の場合のみ実行**

```
Task(
    subagent_type: "pr-review-toolkit:code-reviewer",
    description: "Quality Review: Dev[N] - [タスク名]",
    prompt: """
    以下のファイルの品質検証を行ってください。

    対象ファイル:
    [Developer Agentが作成・修正したファイル一覧]

    チェック項目:
    1. CLAUDE.md 準拠
    2. バグ・潜在的問題
    3. セキュリティ問題
    4. コード品質・可読性

    confidence 80以上の問題を報告してください。
    """
)
```

**Quality Review で問題が見つかった場合:**
1. Developer Agent を再起動して修正
2. 修正後、再度 Quality Review
3. ✅ になるまでループ

#### Step 2.3 完了報告

```
### ✅ Dev1 完了: [タスク名]

**作成ファイル:**
- `path/to/file1.ts` - [簡単な説明]
- `path/to/file2.ts` - [簡単な説明]

**Spec Review:** ✅ 仕様準拠
**Quality Review:** ✅ 品質OK
**テスト:** PASS ✅

**ポイント:**
- [重要な実装ポイントを1-2行で]
```

### Step 2.4: 依存タスクの処理

依存関係があるタスクは、前のタスク完了後に起動:

```
Dev1 完了（2段階レビュー通過） → Dev4 (Dev1に依存) を起動
```

---

## Phase 3: 統合・完了処理

全エージェントの処理が完了したら：

1. **設計との整合性最終確認**
   - Architect役として、全実装が設計書通りか確認

2. **ビルド・テスト確認（証拠必須）**
   - プロジェクトのビルド/テストコマンドを実行
   - **実際にコマンドを実行し、出力を確認すること**
   - エラーがあれば修正

3. **設計書のタスクチェック**
   - 完了したタスクにチェックを入れる

4. **Phase 3 完了報告**

```
## Phase 3 完了 - 統合

### 作成ファイル一覧
| ファイル | 説明 |
|---------|------|
| path/to/file1.ts | [説明] |
| path/to/file2.ts | [説明] |

### ビルド・テスト結果（実行証拠）
コマンド: `[実行したコマンド]`
結果: ✅ 成功（exit 0） / ❌ エラー（修正済み）

→ Phase 4 開始: Quality Gate を実行します
```

---

## Phase 4: Quality Gate（証拠ベース検証）

**Phase 3 完了後、自動的に実行する。**

### 鉄則: 証拠なき完了宣言の禁止

```
完了を主張するには、その場で検証コマンドを実行し、出力を確認すること。
「通るはず」「たぶん大丈夫」は禁止。
```

| 主張 | 必要な証拠 | 不十分な証拠 |
|------|-----------|-------------|
| テスト通過 | テストコマンド出力: 0 failures | 前回の実行結果、「通るはず」 |
| ビルド成功 | ビルドコマンド: exit 0 | リンター通過 |
| バグ修正 | 元の症状が再現しないことを確認 | コード変更した |
| 要件充足 | 設計書と実装の1行ずつ照合 | テスト通過 |

### 実行手順

1. **全テスト実行**
   - プロジェクトのテストコマンドを実行
   - 出力を確認し、失敗数を報告

2. **ビルド確認**
   - プロジェクトのビルドコマンドを実行
   - exit code を確認

3. **設計書との照合**
   - 設計書の各要件を1つずつ確認
   - 実装されていることをファイル:行番号で示す

### Phase 4 完了報告

```
## Phase 4 完了 - Quality Gate

### 検証結果（証拠付き）

**テスト:**
コマンド: `[テストコマンド]`
結果: X/X passing ✅

**ビルド:**
コマンド: `[ビルドコマンド]`
結果: exit 0 ✅

**設計書照合:**
| 要件 | 実装箇所 | 状態 |
|------|---------|------|
| [要件1] | src/xxx.ts:123 | ✅ |
| [要件2] | src/yyy.ts:456 | ✅ |

### 総合判定
✅ PASS / ⚠️ NEEDS WORK / ❌ FAIL

### 次のステップ
- PASS: コミット可能です
- NEEDS WORK: 上記を修正してください
```

---

## Phase 5: 最終報告

Quality Gate が PASS の場合、最終報告を出力:

```
## Swarm開発 完了

### サマリ
- 設計書: [パス]
- Developer Agent: [N]人
- 作成ファイル: [N]件
- 2段階レビュー: 全タスク通過

### 作成ファイル
| ファイル | 説明 |
|---------|------|
| path/to/file1.ts | [説明] |
| path/to/file2.ts | [説明] |

### Quality Gate
✅ PASS（証拠確認済み）

### 次のアクション
コミットする場合：
git add [対象ファイル] && git commit -m "feat: [機能名]"
```

## 重要ルール

1. **証拠なき完了宣言禁止** - 「通るはず」「たぶん」は嘘と同じ
2. **2段階レビュー必須** - Spec → Quality の順序を守る
3. **レビュー問題は修正→再レビュー** - 報告だけで終わらせない
4. **スコープ外エラーは Fix Agent で対処** - 「無視します」は禁止
5. **ポーリング実況は不要** - 「待機中...」の繰り返しはしない
6. **完了時に要約報告** - 各Agent完了時に内容を要約して報告
7. **Developerのみ Task tool で起動** - 独立タスクは並列
8. **TDDを強制** - テストなしのコードは禁止
9. **既存コード確認を強制** - 重複コード禁止
10. **設計逸脱を即座に指摘** - Architect役として監視
11. **Quality Gate 必須** - Phase 4 をスキップしない

## エラー時の対応

### 鉄則: 「スコープ外」でエラーを無視しない

```
エラーを見つけたら、必ず対処する。
「本タスクのスコープ外です」は放置の言い訳にならない。
```

**禁止パターン:**
- 「このエラーは本タスクのスコープ外なので無視します」
- 「既存のエラーなので対応不要です」
- 「関係ないファイルのエラーです」

**正しい対応:**
1. エラーを報告
2. Fix Agent を起動して修正
3. 修正完了を確認してから続行

### スコープ外エラーの処理: Fix Agent

Developer Agent がスコープ外エラーを検出した場合、Orchestrator は即座に Fix Agent を起動する。

```
Task(
    subagent_type: "general-purpose",
    description: "Fix Agent: [エラー概要]",
    prompt: """
    ## 役割: Fix Agent

    ### 検出されたエラー
    [エラーメッセージ全文]

    ### 発生箇所
    [ファイル:行番号]

    ### コンテキスト
    - 元タスク: [Developer Agentのタスク名]
    - 発見状況: [テスト実行時 / ビルド時 / 型チェック時]

    ### 指示
    1. エラーの根本原因を特定
    2. 最小限の修正で解決
    3. 修正後、関連テストを実行して確認
    4. 他に影響がないことを確認

    ### 制約
    - 本来のタスクには手を出さない
    - エラー修正のみに集中
    - 過剰な修正・リファクタリングは禁止

    ### 報告形式
    ## Fix完了報告

    ### 原因
    [根本原因]

    ### 修正内容
    - [ファイル:行番号]: [変更内容]

    ### 検証結果
    - 実行コマンド: [コマンド]
    - 結果: PASS/FAIL
    """
)
```

### Fix Agent のフロー

```
Developer Agent がエラー検出
    ↓
「スコープ外」と判断
    ↓
Orchestrator に報告（エラー詳細付き）
    ↓
Orchestrator が Fix Agent を起動（バックグラウンド）
    ↓
Developer Agent は本来のタスクを続行
    ↓
Fix Agent 完了後、Orchestrator が結果を確認
    ↓
修正失敗の場合 → ユーザーに報告
```

### 並列処理の注意

- Fix Agent と Developer Agent が同じファイルを触る場合は直列化
- 独立したエラー（別ファイル）なら並列で処理可能
- 複数エラーは1つの Fix Agent にまとめても良い

---

### Developer Agent がエラーで終了した場合

1. エラー内容を報告
2. 修正が必要な場合は再起動または手動修正
3. 設計に問題がある場合はユーザーに確認

### Spec Review で問題が見つかった場合

1. 具体的な問題を報告（ファイル:行番号）
2. Developer Agent を再起動して修正
3. 再度 Spec Review を実行
4. ✅ になるまでループ

### Quality Review で問題が見つかった場合

1. 重要度別に問題を報告
2. CRITICAL/HIGH は修正必須
3. Developer Agent を再起動して修正
4. 再度 Quality Review を実行
5. ✅ になるまでループ

### ビルドエラーの場合

1. エラー内容を報告
2. 該当ファイルを修正
3. 再ビルドで確認（コマンド実行＋出力確認）

### Quality Gate が FAIL の場合

1. CRITICAL 項目を報告
2. 修正方法を提案
3. ユーザーの指示を待つ（自動修正しない）
